RCS Attitude Control Experiments

Test — Torque Balance

testGuide
FAIL
Target
Every tick, derive current total torque on the body and fire RCS with exactly the opposing torque. See if RCS alone can hold AoA ≈ 0 during a max-throttle launch with gimbal fixed at 0.
Approach
targetTorque = −τ_total (each snapshot, no memory)
GuideRCS.targetTorqueRcs() converts to per-pod duty.
What happened
Limit cycle. Jump → zero → jump → zero at ~2 Hz on the telemetry torque trace, until RCS saturated, then a monotonic drift to crash.
Why it failed
  • Deadband release: below 100 N·m the guide sent cmdRcsDuty(null), relinquishing control. Next snapshot saw torque back and re-fired. Classic bang-bang limit cycle.
  • Snapshot rate mismatch: 20 Hz throttle (later fixed to 80 Hz) put guidance 4 physics ticks behind.
  • Snapshot is one tick stale: the torque it reacts to has already evolved before the command lands.
limit-cycle deadband-release latency

Predictive Torque Cancel

predictiveTorque
FAIL
Target
Instead of reacting to past torque, predict the next tick's drag torque from current state and command RCS to cancel it before it happens.
Approach
predict state at t+dt (no RCS assumed)
τ_drag_next = derive(predicted state).torqueDrag
targetTorque = −τ_drag_next
fire RCS via GuideRCS
What happened
Ran for a while looking great — torque trace smooth and low. Then attitude suddenly broke away and rocket crashed.
Why it failed
  • Prediction assumes no RCS, but RCS is firing. Each shot shifts lateral velocity → AoA grows → drag torque prediction goes stale by the time command lands.
  • Small residual (200–500 N·m) per tick in a CP-above-CoM instability compounds exponentially.
  • Pure feedforward has no rate/attitude feedback to absorb drift.
feedforward-only positive-feedback model-mismatch

Predictive + PID

predictivePlus
FAIL
Target
Add classical PID on top of feedforward — proportional attitude hold (vs local vertical), rate damping, and an integral term to absorb slow biases.
Approach
targetTorque = −τ_drag_predicted     // feedforward
             − K_p·(θ − θ_target)    // attitude hold
             − K_d·ω                 // rate damping
             − K_lead·dτ_drag/dt     // phase lead
             + K_i·∫err              // bias correction
What happened
Better than feedforward alone — the crash was delayed, but ultimately same outcome. Attitude wandered off, RCS saturated, rocket flipped.
Why it failed
  • PID is reactive; by the time it reacts to attitude drift, the drift has had several ticks to grow.
  • Latency between snapshot and command application (~1–2 ticks) is unaccounted-for in the loop.
  • CP-above-CoM instability requires phase advance that PID can't provide without high gain — and high gain saturates RCS.
reactive-only latency-unmodeled gain-vs-saturation tradeoff

Predictive + PID + AoA Impulse

predictivePlusAoA
SUCCESS · NOT PRACTICAL
Target
Add a periodic "AoA impulse" term — every 3rd tick, fire full RCS torque proportional to AoA. Intent: kick AoA toward zero faster than PID can.
Approach
// tick N   → check AoA > threshold, arm pending
// tick N+1 → fire 2·I·AoA/dt² (way above RCS max → fully saturated)
// tick N+2 → skip
// repeat
What happened
Actually worked — the manual test with an initial east tilt ran all the way up with AoA staying bounded. This was the first guide that did not crash.
Why "not practical"
  • Fires RCS at 100% saturation every third tick, consuming propellant aggressively.
  • Relies on huge torque overshoots that only work because RCS is cheap in this sim. In a real system this would burn through cold-gas budget in seconds.
  • Bang-bang behaviour — no graceful scaling.
propellant-waste bang-bang first-non-crash

Predictive + PID + AoA + East Push

predictivePlusAoAPush
FAIL
Target
Prefix the successful predictivePlusAoA with a timed east-tilt phase (S seconds), then hand off to AoA chase. Later iterations added west-reversal and cadence-based nudges.
Approach
Phase machine — east (S sec) → west (ω-crossing) → chase (predictivePlusAoA verbatim).
What happened
Multiple iterations, all unstable. West-reversal overshot ω (adding a second-tick delay before AoA chase engaged). Cadence push built drift. Simple east prefix destabilised when the AoA-chase phase inherited a nonzero ω.
Why it failed
  • θ_target sign flip bug — for several iterations the AoA-zero direction was computed as atan2(relVx, -relVy) instead of atan2(-relVx, relVy). 180° error meant the guide was holding the rocket upside-down.
  • After sign fix, D-term on dAoA was unconditionally braking — fighting reductions in AoA as well as increases.
  • Sweep and chase phase interacted badly: sweep left ω residual that chase had to absorb, and the impulse governor kept re-arming, compounding.
sign-flip-bug phase-coupling impulse-governor-race

Verify: Prediction Accuracy

predictVerifier
DIAGNOSTIC
Target
Prove (or disprove) that the prediction chain — next-tick drag torque, AoA, altitude, dynamic pressure — is actually accurate. No RCS, no gimbal, only derive math.
Approach
Predict state at N+1, store. Next tick, compare predicted values against the actual snapshot's derive output. Only count 1-tick gaps; skip duplicates and misses.
Result
Prediction is essentially exact. 
τ: mean |err| ≈ 0–1 N·m   out of  9,000–40,000 N·m
α: mean |err| ≈ 6e-6 degrees
Q: mean |err| ≈ 0 Pa
drag: mean |err| ≈ 0 N
Floating-point-level agreement between predictor and physics.
Takeaway
All the failures were controller problems, not prediction problems. This diagnostic retired a whole class of suspicion and pointed cleanly at the actuation/latency pipeline.
diagnostic retired-hypothesis prediction-is-trustworthy
Gimbal Attitude Control Experiments

Gimbal: 2-tick Predictive

gimbalPredictive2
ACCURATE WIN
Target
Use the engine gimbal (not RCS) to autonomously cancel drag torque during ascent. Match predicted future-tick drag torque with gimbal torque by commanding the correct rate before the tick where it needs to act.
Key insight
Physics integrates gimbal rate one tick at a time. Guidance replaces the rate every snapshot. So a "2-tick pipeline" only needs to compute the rate that lands gimbal on target at the next tick — predicting two ticks ahead and issuing a rate for tick N+2 caused repeated overshoot/undershoot because the rate was overwritten before it finished acting.
Approach
// current tick N
g_N = current gimbal angle
g_N1 = g_N + R_N·dt                       // committed
S_N1 = predict(S_N, gimbal = g_N1)
τ_drag_N1 = derive(S_N1).torqueDrag

// Solve gimbal torque: A·cos(g) + B·sin(g) = −τ_drag_N1
g_req = asin(−τ_drag_N1 / R_amp) − φ
g_req = clamp(g_req, ±GIMBAL_MAX_DEG)

// Rate so gimbal lands on g_req at N+1
R_cmd = clamp((g_req − g_N)/dt, ±GIMBAL_RATE_DEG_S)
send(setGimbalRate(R_cmd))
Result
Rock solid. Total torque held at 100–150 N·m at low altitude, then as the rocket climbed and drag faded, held steady at 1 N·m for over a minute. Attitude never drifted more than a fraction of a degree. No RCS, no propellant waste.
Why it works
  • Gimbal is continuous — one rate command integrates smoothly within the tick. No pulsed duty-cycle timing mismatch like RCS.
  • Prediction is exact (proven by predictVerifier), so the solved g_req matches the actual torque requirement.
  • 1-tick horizon correctly matches the pipeline: predict, solve, command — all in the same tick, gimbal ready by next.
  • Angle and rate clamps handled gracefully; saturation simply caps the achievable torque rather than destabilising.
continuous-actuator predictive-solve 1-tick-horizon accurate
Lessons That Survived Every Iteration
Actuator choice
Continuous actuators (gimbal) are easier to control precisely than pulsed/duty-cycle actuators (RCS). Latency is baked into RCS at the hardware level; gimbal integrates smoothly.
Horizon
A control horizon must match the actuator's actual integration step. Predicting 2 ticks ahead when the rate gets overwritten every tick just causes oscillation. 1-tick pipeline is correct for the current architecture.
Prediction > feedback
Once prediction is verified accurate, feedforward-solve beats PID for this problem. PID's job was to mask the deeper problem (model mismatch); with a correct model, PID has nothing left to do.
Diagnose before tuning
Five failures were spent tuning PID gains while the actual culprit was either sign conventions, horizon mismatch, or actuation latency. predictVerifier should have come first.
